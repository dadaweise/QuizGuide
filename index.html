This one compiles, so check it once the server runs. complete_task sets availability: Set(1) ("1 itu Available"), but dispatch_operator never sets it back to 0:

rust
let operator_active = OperatorActiveModel {
    id: ActiveValue::Unchanged(operator_id),
    ..Default::default()            // nothing is Set, so availability never changes

Option A · Sort in React

range(c) already gives the distance from a courier to the selected item's pickup (0 when no item is selected). Decide the order before you code:

  1. Available couriers first (they are the only ones you can pick).
  2. Then nearest to the pickup.
  3. Then by specialty: alphabetical, with "No specialty" last. When no item is selected all distances are 0, so this groups couriers by specialty.

async fn recommend_couriers(&self, order_item_id: i32) -> Result<Vec<OperatorDetailsResponse>, StatusCode> {
    if order_item_id <= 0 {
        return Err(StatusCode::BAD_REQUEST);
    }

    let order_item = self.repository.get_order_item(order_item_id).await;
    if let Err(DbErr::RecordNotFound(_)) = order_item {
        return Err(StatusCode::NOT_FOUND);
    }
    if order_item.is_err() {
        return Err(StatusCode::INTERNAL_SERVER_ERROR);
    }

    let order_item = order_item.unwrap();

    // Titik pickup (manufacturer) untuk jarak
    let mut pickup = (0.0, 0.0);
    if let Some(medicine) = order_item.medicine.into_option() {
        if let Some(manufacturer) = medicine.manufacturer.into_option() {
            pickup = (manufacturer.x_position, manufacturer.y_position);
        }
    }

    let mut destination_region = None;
    if let Some(order) = order_item.order.into_option() {
        if let Some(warehouse) = order.warehouse.into_option() {
            destination_region = Some(warehouse.region_id);
        }

        if operator.role_id == 2 {
            couriers.push(operator);
        }

6.0a Two decisions, re-checked against the book

Swimlanes: two (actor and system), not three

  1. What the book draws. Every activity diagram the book draws for a single use case has two lanes: Customer | System in Fig. 5-4, Shipping clerk | System in Fig. 5-5 (PDF 167–168) and LibraryEmployee | System in Fig. 13-32 (PDF 466). PDF 173 adds that the line between the two lanes is the system boundary. Lanes for several agents, including other systems, appear in Fig. 2-14 (PDF 90). That figure is a workflow across a whole business process, not one use case.
  2. Why the app/server split is not a lane. React, Tauri and Axum are one system to the Dispatcher. How the work is split across them is a design decision, and the multilayer sequence diagram is where the book shows design layers (Ch. 13). A third lane would put design into an analysis diagram, and the same split would then be drawn twice.
  3. What changes in the diagram. The "Send … request" action disappears, because sending a request is a design detail. What the screen already shows when the use case starts (the lists, the active order) is not drawn either; it is a precondition (next section). The 503 "server unreachable" branch also leaves the activity diagram (perfect technology assumption, PDF 109). It stays in the sequence diagram, where the Tauri client produces it.
  4. If your lecturer asks for three. The notation still allows it, because a lane may be a system (PDF 90). Draw the third lane only if asked, and then keep every server check in the server lane in the same order as the code.

Preconditions are not activities

The book keeps the state that must hold before a use case in the use case description, not in the activity diagram:

  1. Where the book puts them. The fully developed description has separate compartments for Preconditions, Postconditions and Flow of activities (Fig. 5-2, PDF 164; Fig. 5-3, PDF 166). PDF 165 defines a precondition as "what the state of the system must be for the use case to begin", including "the condition of the actor prior to beginning the use case".
  2. What the activity diagram is. It documents the flow of activities. PDF 167 says it "can take the place of the flow of activities section". So it contains only what that section contains: the actor's steps and the system's responses.
  3. How the book's own figures start. Create customer account (Fig. 5-4) starts at "Request account", which is flow step 1 after the triggering event (Fig. 5-2). Ship items (Fig. 5-5) starts at "Lookup Sale with SaleItems", and its preconditions "Sale must exist. Sale items must exist" (PDF 166) are not drawn anywhere in the diagram.
  4. What is not drawn. "Open the Courier page as this courier" (the actor's condition before starting), "Show the ASSIGNED active order…" (the item must already be ASSIGNED), and "Show each available courier's distance" (a list that is already on screen). All three are state before or around the use case, not steps of its flow.
  5. What stays, and why. (a) The decisions with guards, such as "other status: 400". The book lists the ways a flow can fail as Exception conditions next to the flow steps (Fig. 5-2, "1.1 Basic customer data are incomplete"), and the server tests these conditions in code, so the diagram shows them. A precondition is a state that should hold; the guard is the system checking it. (b) The actor's inputs: selecting the order item and the courier are the inputs of the use case (they are the two ids), like "Enter addresses" in Fig. 5-4.

How the checks are drawn: a condition on one message
  1. The book's notation. A message may start with a true/false condition: [true/false condition] return-value := message-name (parameter-list). "If it evaluates to true, the message is sent. If it evaluates to false, the message isn't sent" (PDF 172). The book's design diagram uses it as [firstItem]createCart ( ) (Fig. 13-15, PDF 443), and PDF 446 lists "true/false conditions" as one of the parts you add to every message.
  2. What it stands for in Rust. Every if … { return Err(StatusCode::X); } sends exactly one message: the error return to the caller. So it is one dashed return with the if as its condition, [not ready] Err(400), drawn right after the message that got the data being tested.
  3. What happens to the messages below it. A return ends the method, so the messages below it are sent only when the condition was false. The book says the same for its example: "if it is not the first item, then this sequence of messages is skipped" (PDF 444). The diagram states this once in a note on the Tauri command's lifeline (notes may go on any UML diagram, PDF 171), so the later messages need no repeated [else].
  4. Where a frame is still used. The book's own advice is that one condition is shorter, but when several messages depend on the same test "the frame is more explicit and precise" (PDF 172). The reply going back through four layers is that case: alt [Ok(())] / [Err(status)], one operand per arm of the match in server.rs and the Tauri command. It also keeps the project rule that every sequence diagram has at least one fragment.
  5. Which frames exist. The book teaches only Loop, Alt and Opt (PDF 172–173, 439). break, ref and par do not appear in it, so do not use them in the quiz.

What decides where a method goes. A message must be sent in a use case realization (PDF 408, 440, 455), and it goes to the object that owns the data and can be reached from the sender (PDF 434–436). A check on one object's own fields, or a change to them, is that object's method. A calculation that needs two objects goes on the one with the main data, and the other object's data comes as a parameter (distanceTo(x, y) on Operator, with the position from getPickupLocation() or getDestination()). Repository calls, status-code mapping and HTTP handling are not domain methods. In the Rust code the checks are written inline in Service and the entities are plain data; the methods are the book's reading of that code.
